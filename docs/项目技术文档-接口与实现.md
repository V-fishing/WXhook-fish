## 1. 项目概述

### 1.1 项目做什么

从**运行中的微信 4.x 进程内存**提取数据库加密密钥,解密本地 SQLCipher 加密数据库,
并衍生出一整套数据工具(实时监听 / 批量导出 / 图片解密 / 语音转录 / 朋友圈解析)。

### 1.2 能读到什么数据(数据边界)

| 数据 | 存储位置 | 可读范围 |
|---|---|---|
| **聊天记录** | 本地 `message_0~3.db`(全量) | ✅ **全部历史消息**(文本/图片/语音/视频/文件引用) |
| **会话列表** | 本地 `session.db` | ✅ 全部会话+最新消息摘要 |
| **联系人** | 本地 `contact.db` | ✅ 全部缓存对象(好友+群+公众号+群成员缓存,含已删除) |
| **朋友圈** | 本地 `sns.db`(**滚动缓存**) | ⚠️ **最近刷到过的**动态+互动(约 7000+ 条;云端母本不可及) |
| 图片 | 本地 `.dat` 加密文件 | ✅ 全部(需 image key) |
| 语音 | 本地 SILK 文件 | ✅ 可转录为文本 |
| 收藏/表情/头像 | 本地各库 | ✅ |
| **云端独占数据** | 腾讯服务器 | ❌ 不可及(未缓存的朋友圈、好友关系链全量等) |

### 1.3 技术路线的本质(与 Hook 方案的对比)

```
本项目: 纯只读路线                Hook 方案(wxhelper/千寻等):
  内存扫描(读) → 拿密钥              注入 DLL → 改执行流 → 拦截/调用内部函数
  读盘 → 解密副本 → SQL 查询
                                    实时性: 毫秒级
  实时性: 秒级(轮询间隔)             功能: 可发消息(调用内部Call)
  功能: 只读(不能发消息)             风险: 高(模块暴露/内存CRC/注入检测)
  风险: 极低(零注入零修改!)
```

**适用判断**:需要"读数据"(存档/分析/监听/AI 记忆库)→ 本项目;
需要"写数据"(自动发消息/机器人)→ Hook 类方案(风险自担)。

### 1.4 支持平台与版本

| 平台 | 微信版本 | 密钥提取 | 解密 | 实时监听 |
|---|---|---|---|---|
| Windows | 个人微信 4.0 ~ **4.1.13**(实测✓) | `find_all_keys_windows.py` | ✅ | ✅ |
| Windows | 企业微信 5.x | `find_wxwork_keys.py` | ✅(wxSQLite3 AES-128) | ✅ |
| macOS | 4.x | `find_all_keys_macos.c`(需重签名) | ✅ | ✅ |
| Linux | 4.x | `find_all_keys_linux.py` | ✅ | ✅ |
| 旧版 3.x | WeChatWin.dll 时代 | ❌ 不适用(密钥体系不同) | ❌ | ❌ |

## 3. 核心原理

### 3.1 微信 4.x 的数据库加密体系

微信 4.x 使用 **WCDB**(腾讯自研 SQLite 封装)+ **SQLCipher 4** 参数加密:

| 参数 | 值 |
|---|---|
| 加密算法 | **AES-256-CBC** |
| 完整性校验 | **HMAC-SHA512**(每页一个,存于页尾) |
| 页大小 | **4096 字节** |
| 密钥长度 | **32 字节**(64 hex 字符) |
| 盐长度 | **16 字节**(32 hex 字符,存于文件头前 16 字节,**明文**) |
| 每页保留区 | **80 字节** = IV(16) + HMAC(64) |
| 密钥派生 | 每库独立随机密钥;HMAC 密钥 = `PBKDF2-SHA512(enc_key, salt⊕0x3A, 2轮)` |

**每页的物理布局:**

```
普通页(pgno > 1):
┌──────────────────────────── 4096 字节 ────────────────────────┐
│  AES-256-CBC 密文(4016B)          │ IV(16B)  │ HMAC(64B)     │
└───────────────────────────────────────────────────────────────┘
     ↑ 用 enc_key + 本页IV 解密         ↑ 解密后填充 80B 零

第 1 页(pgno = 1)特殊:
┌──────────────────────────── 4096 字节 ────────────────────────┐
│ 盐(16B,明文) │ 密文(4016B)        │ IV(16B)  │ HMAC(64B)   │
└───────────────────────────────────────────────────────────────┘
  ↑ 解密后开头还原为 "SQLite format 3\x00" 标准头
```

### 3.2 密钥为什么在内存里?为什么能扫到?

- 每个库文件的密钥在**库创建时随机生成**,之后**永不轮换**(跨登录/跨重装稳定——实测 5月 与 9月 完全一致!)
- WCDB 打开库时会把密钥以 **十六进制字符串形式缓存在进程内存**,格式为:

```
x'<64位hex密钥><32位hex盐>'      ← 完整形态(96 hex)
x'<64位hex密钥>'                 ← 只有密钥(64 hex)
x'<更长hex串,首64是密钥尾32是盐>'  ← 长形态
```

- 扫描器用正则 `x'([0-9a-fA-F]{64,192})'` 在进程内存里找所有候选串,
  再**逐个用 HMAC-SHA512 验证**(拿候选密钥试解库文件第 1 页,校验通过才算真密钥)
  ——**验证机制保证零误报**。
- **这是纯只读操作**(OpenProcess + ReadProcessMemory),不注入、不写、不 Hook,
  因此不触发微信的注入检测/内存 CRC/文件自检(实测 4.1.13.65 无任何异常提示)。

### 3.3 密钥的生命周期(重要!决定维护成本)

| 场景 | 密钥是否变化 |
|---|---|
| 登录/退出/重启微信 | ❌ 不变 |
| 重装微信(保留 `D:\xwechat_files` 数据目录) | ❌ 不变(实测:5月与9月密钥完全一致) |
| 换账号登录 | ⚠️ 不同账号 = 不同数据目录 = 不同密钥 |
| 微信大版本迁移重建数据库 | ⚠️ 新文件新密钥(重扫即可) |
| 删除数据目录 | ⚠️ 全新密钥 |

**维护规则:监控/解密出现 HMAC 失败时,重跑一次密钥提取(5 秒)即可。**

## 4. 模块详解:密钥提取

### 4.1 流程(`find_all_keys_windows.py` + `key_scan_common.py`)

```
① 发现微信进程
   tasklist /FI "IMAGENAME eq Weixin.exe" → 按内存降序排列(主进程内存最大,密钥几乎都在它)

② 收集数据库文件(磁盘侧)
   遍历 config.db_dir → 每个 .db 文件读第 1 页 → 提取明文盐(前16字节)
   → 建立 salt → [库文件] 映射表(同盐=同库)

③ 定位 ntdll!NtReadVirtualMemory 等备用 API(可选)
   主路径:kernel32.ReadProcessMemory

④ 逐进程扫描内存
   VirtualQueryEx 枚举 MEM_COMMIT 且可读的区域
   → 分块读入 → 正则匹配 x'([0-9a-fA-F]{64,192})'
   → 对每个候选:
       长度=96: 前64=密钥, 后32=盐 → 盐在待找集合? → HMAC验证 → 入库
       长度=64: 纯密钥 → 对所有未匹配盐逐一 HMAC 验证
       更长:   首64=密钥, 尾32=盐

⑤ 交叉验证(cross_verify_keys)
   对仍未匹配的盐:尝试用已确认的其他密钥去开(同账号的库可能共用密钥场景)

⑥ 保存 all_keys.json
   { "message\\message_0.db": {"enc_key": "...", "salt": "...", "size_mb": ...}, ... }
```

### 4.2 关键实现细节

- **HMAC 验证公式**(与 SQLCipher 4 规范一致):

```python
mac_salt = bytes(b ^ 0x3A for b in salt)                 # 盐异或 0x3A
mac_key  = pbkdf2_hmac("sha512", enc_key, mac_salt, 2, dklen=32)  # 仅 2 轮迭代!
hmac_data   = page1[16 : 4096-80+16]                      # 密文+IV 区
stored_hmac = page1[4096-64 : 4096]                       # 页尾 64 字节
校验: HMAC-SHA512(mac_key, hmac_data + pack('<I', 1)) == stored_hmac
                                       ↑ 页号小端 4 字节参与计算
```

- **性能**:实测 4.1.13(主进程 374MB / 1065MB 扫描区)全量扫描 **5.4 秒**;
  因为候选验证是"先看盐是否在待找集合"的 O(1) 命中,真正做 HMAC 的次数很少。
- **权限要求**:管理员(读其他进程内存);微信需处于**已登录**状态(密钥缓存在登录后建立)。

### 4.3 实测结果(4.1.13.65)

```
结果: 23/26 salts 找到密钥(5.4秒)
  OK: message_0~3.db / biz_message_0~2 / session.db / contact.db / sns.db ... (23个)
  MISSING: chatbot_message.db / weclaw.db / third_app_icon.db(未使用过的库,内存无缓存,无影响)
```

## 5. 模块详解:数据库解密

### 5.1 逐页解密算法(`decrypt_db.py`)

```python
对每个 4096 字节页:
    iv         = page[4016 : 4032]                    # 取本页 IV
    if 第1页:
        明文 = b"SQLite format 3\x00" + AES_CBC解密(page[16:4016]) + 80B零
    else:
        明文 = AES_CBC解密(page[0:4016]) + 80B零
    写入输出文件
解密前先做第1页 HMAC 验证(密钥错误立即报错,不产生垃圾文件)
解密后用 sqlite3 打开验证表结构(自动确认解密正确性)
```

### 5.2 CLI 接口

```bash
python decrypt_db.py                  # 解密全部(从小到大排序)
python decrypt_db.py -i               # 增量模式(源文件 mtime 未变则跳过)
python decrypt_db.py --dry-run        # 预览将解密哪些库
```

### 5.3 输出

- 目录:`decrypted/`(镜像 `db_storage` 的子目录结构)
- 自动清理验证时残留的 `-shm`/`-wal` 空文件(避免后续打开读到旧 WAL 报 malformed)

## 6. 模块详解:实时消息监听

### 6.1 监听原理(为什么"轮询"也能叫实时)

```
微信收到消息 → 微信自己写 session.db(它自己的正常行为,毫秒级)
                     ↓ (磁盘文件已更新)
monitor.py 每 3 秒:
  ① 把 session.db 解密到内存(bytes) → 写临时文件 .tmp_monitor
  ② sqlite3 打开 → 读 SessionTable 全表(会话状态快照)
  ③ 与上一轮快照逐会话对比 last_timestamp
  ④ 时间戳变新 = 该会话有新消息 → 打印
  ⑤ 快照滚动,进入下一轮
```

**为什么不监听 message 库?** session.db 只有 **2MB**(解密<1秒),
而 message 库 500MB+——先用会话摘要实现秒级感知,V2 再升级消息库拿完整内容。

### 6.2 核心数据:SessionTable(会话表)

```sql
SELECT username,              -- 会话对象(wxid_xxx / xxx@chatroom / gh_xxx)
       unread_count,          -- 未读数(红点数字!)
       summary,               -- 最后一条消息摘要(可能是 zstd 压缩的!)
       last_timestamp,        -- 最后消息时间戳(秒)
       last_msg_type,         -- 消息类型码
       last_msg_sender,       -- 最后发送者 wxid(群聊场景)
       last_sender_display_name
FROM SessionTable WHERE last_timestamp > 0
```

> ⚠️ 细节:`summary` 部分记录是 **zstd 压缩**的(监控器里 `_zstd_dctx.decompress` 处理);
> 群消息的 summary 格式为 `"发送者wxid:\n内容"`,代码里按 `':\n'` 切分提取纯内容。

### 6.3 消息类型码映射

| type | 含义 | type | 含义 |
|---|---|---|---|
| 1 | 文本 | 43 | 视频 |
| 3 | 图片 | 47 | 表情 |
| 34 | 语音 | 48 | 位置 |
| 42 | 名片 | 49 | 链接/文件 |
| 50 | 语音/视频通话 | 10000 | 系统消息 |
| 10002 | 撤回 | | |

### 6.4 输出格式

```
[14:23:45] [张三]                    ← 私聊(昵称来自contact.db映射)
  [文本] 你好,测试一下
  (未读: 1)

[14:24:02] [某某群] 李四:            ← 群聊(额外显示群内发送者)
  [文本] 大家好
```

### 6.5 性能与资源

| 指标 | 值 |
|---|---|
| 单轮开销 | session.db 2MB 解密 < 1秒(AES-CBC 纯 Python 约 0.6s) |
| CPU 占用 | 轮询瞬间单核 ~30%,平均 <5% |
| 内存 | 常驻 ~30MB(主要是联系人映射) |
| 消息延迟 | 平均 1.5~4.5 秒(3 秒轮询 + 解密时间) |
| 对微信影响 | **零**(纯读盘;连进程都不访问!) |

### 6.6 局限与 V2 方向

| 局限 | 原因 | V2 方案 |
|---|---|---|
| 只有"最后一条"摘要 | SessionTable 天然是会话级 | 轮询 `message_*.db` 的 Msg 表(每条消息一行) |
| 一次多条只看到最后 | 同上 | 增量游标(记录上次最大 msgId,只取新增) |
| 摘要可能截断 | 会话列表预览本身截断 | Msg 表有完整 content |
| 无法回溯历史 | 只对比"状态" | V2 顺带获得全量历史查询能力 |

## 7. 模块详解:聊天记录导出

### 7.1 导出管线(`export_all_chats.py` → `export_messages.py`)

```
decrypted/message/message_0~3.db (明文库,4个分库)
        ↓ 按会话聚合(glob message_*.db,解析每个库的 Chat* 表)
chat_data[会话wxid] = {显示名, 是否群聊, 消息列表}
        ↓ 富化
   · contact.db → 昵称/备注映射
   · message_resource.db → ChatName2Id + MessageResourceInfo → 文件MD5映射
   · 群聊成员名解析(群消息 sender 定位到成员昵称)
        ↓ 多格式输出到 <output_base_dir>/<会话名>/
   messages.json(结构化) / messages.csv(表格) / messages.html(可读排版,含图片内嵌)
        ↓ 可选:--with-transcriptions
   语音消息 SILK → WAV → Whisper 文本(三后端:local/OpenAI/whisper.cpp)
```

### 7.2 消息库的关键表(4.x)

| 库/表 | 内容 |

## 8. 模块详解:图片解密

### 8.1 三代格式(`decode_image.py`)

| 格式 | 识别 | 加密 | 解法 |
|---|---|---|---|
| **旧 XOR** | 无 V1/V2 签名 | 单字节 XOR(key 未知) | **自动检测**:拿文件头与已知图片 magic(JPG=FFD8FF / PNG=89504E47 / GIF / WEBP / BMP)比对反推 key |
| **V1** | `07 08 V1 08 07` | 固定 key | 内置 |
| **V2**(2025-08+) | `07 08 V2 08 07`(6字节签名) | **AES-128-ECB + XOR 混合** | 需 `image_aes_key`(16字节 ASCII)+ `image_xor_key`(如 0x88),从微信进程内存提取 |

```
V2 文件结构:
[6B 签名 07 08 V2 08 07][4B aes_size LE][4B xor_size LE][1B padding]
[AES 加密区: aes_size 字节][XOR 加密区: xor_size 字节]...
```

### 8.2 使用

```bash
# 批量:扫描 attach 目录全部 .dat,镜像目录输出明文图树
python main.py decode-images
python main.py decode-images --attach-dir D:\xwechat_files\<wxid>\msg\attach \
                             --decoded-dir D:\my_pics --force
# 无需微信在运行、无需 DB 密钥(V2 需要 image_aes_key 已配置)
```

## 9. 模块详解:朋友圈(SNS)

### 9.1 数据边界(重要认知)

```
朋友圈 = 云端母本(不可及) + 本地滚动缓存(可读!)
本地 sns.db 存的是"你最近刷到过的"动态(实测 7265 条)
  + 你自己发的(发布任务/草稿表)
  + 收到的评论/点赞通知(SnsMessage_tmp3,实测 3447 条)
  + 甚至推送过的广告(SnsAdTimeLine)
旧内容会被挤出缓存(滚动窗口机制) → 想长期留存需定期导出!
```

### 9.2 sns.db 核心表结构(实测)

| 表 | 行数(实测) | 内容 |
|---|---|---|
| `SnsTimeLine` | 7265 | **每条动态一行**:`tid` + `user_name`(发布者) + `content`(**XML:文字/媒体列表/点赞/评论全套!**) + `pack_info_buf` |
| `SnsMessage_tmp3` | 3447 | 评论/点赞通知(local_id, from/to, content, feed_id) |
| `SnsTopItem_1` | 40662 | 每好友未读/已读标记 |
| `SnsAdTimeLine` | 少量 | 广告曝光记录 |
| `SnsDraft` / `SnsPublishTask` | — | 自己的草稿/发布任务 |

### 9.3 技术要点(`export_sns.py`)

- `SnsTimeLine.content` 存在 **4 种编码形态**(不同版本/时段):解 XML 前需 `_decode_sns_content_blob` 统一(zstd 解压 / 直接 XML / 二进制 blob…)
- XML 是"伪 XML"(有非法片段),需 `_sanitize_sns_pseudo_xml` 清洗后再解析
- 朋友圈图片缓存在独立目录,`.dat` 加密 → `_decrypt_sns_dat` 解出 → 按 feed 组织成 **HTML 时间线**

```bash
python export_sns.py    # 导出全部缓存动态 + 图片 → HTML 时间线
```

## 15. 检测风险与安全边界

### 15.1 风险矩阵

| 操作 | 检测面 | 风险评级 |
|---|---|---|
| 内存扫描提密钥 | OpenProcess+读(工具链常态行为) | 🟢 极低 |
| 读盘解密 | 纯文件读取(微信无感知) | 🟢 极低 |
| 轮询监听 | 同上 | 🟢 极低 |
| 导出/图片解密 | 纯读盘 | 🟢 极低 |
| **(对比)DLL 注入+Hook** | 模块列表/内存CRC/执行流 | 🔴 高(本项目刻意不含!) |

### 15.2 行为风控(服务端,唯一真正的风险源)

- 本项目**只读不发**,不产生异常行为模式 → 风险主要来自你**账号本身的使用**
- 铁律:测试用小号;不要把导出能力用于他人数据(违法!)

### 15.3 合规提醒

- 仅处理**自己账号**的数据;访问他人微信数据违法
- 聊天记录含敏感个人信息,导出文件妥善保管(明文库=裸数据!)

## 16. 故障排查

| 症状 | 原因 | 解决 |
|---|---|---|
| `未检测到微信进程` | 4.x 进程名是 **Weixin.exe**(不是 WeChat.exe!) | 确认微信已登录;检查 config 的 `wechat_process` |
| 密钥提取 0 命中 | 数据目录选错(多账号)/微信刚启动密钥未缓存 | 核对 `db_dir` 的 wxid;登录后等几秒重试 |
| `HMAC验证失败` | 密钥过期(库文件重建/换号) | 重跑 `find_all_keys_windows.py`(5秒) |
| `database disk image is malformed` | 残留旧 `-wal`/`-shm` | 删除明文库旁的这两个文件(新版已自动清理) |
| summary 显示 `(压缩内容)` | zstd 解压失败(截断的库副本) | 正常现象(会话摘要截断);V2 读消息库解决 |
| 监听有漏/延迟 | 轮询间隔内多条消息只报最后一条 | V2(轮询 message 库增量)解决 |
| 图片解密 skipped_no_key | 未配置 `image_aes_key` | 从微信进程内存提取 V2 key(见 README 图片章节) |
| 企业微信库打不开 | 加密体系不同(wxSQLite3 AES-128) | 使用 `wxwork_*` 专用脚本 |
