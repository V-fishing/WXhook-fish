## 二、架构

```
微信发送管线: UI → UP2 → UP1 0x1790970 → CORE → CGI → 网络
                            ↑
   ┌────────────────────────┴──────────────────────────┐
   │ wx_send.dll (注入到 Weixin.exe 内)                  │
   │                                                    │
   │ UP1 入口 12B 补丁: mov rax,stub ; jmp rax          │
   │   ↓ jmp 进入 (栈顶=原始调用者返回地址,不可用 C 直接待)│
   │ asm stub: push rcx/rdx/r8/r9 → call C_helper(r8)   │
   │           → pop → mov rax,[g_trampoline] → jmp     │
   │ C_helper: vtable 校验(0x8BDF0F8) → 队列非空 →       │
   │           改写 obj+0x758(content) / obj+0xB0(wxid) │
   │ trampoline: 原 17B 指令 + jmp UP1+17                │
   │                                                    │
   │ 控制: \\.\pipe\wxsend  协议: SEND|target|b64\n      │
   │       STATUS → hits/queue/rewrites/vtmiss/drop      │
   └────────────────────────────────────────────────────┘
```

### 关键工程决策

1. **为什么需要 asm 桩**:UP1 被 `jmp` 进入时栈顶返回地址属于原始调用者,C 函数的
   `ret` 会跳回错误位置。桩先保存 4 个参数寄存器,call C 辅助(此时栈 16 对齐:
   entry rsp≡8 → push×4 → sub 0x28 → ≡0),恢复寄存器后 jmp trampoline。
2. **零分配改写**:新内容 ≤ 原字符串 cap 时,SSO(cap≤15)写内联缓冲、
   cap>15 写既有堆缓冲,再更新 size——不触碰微信堆管理器,无任何分配/释放。
3. **prologue 字节校验**:安装前比对 17 字节签名(`55 41 57 41 56 56 57 53
   48 83 ec 78 48 8d 6c 24 70`),版本不匹配即拒绝安装(防呆)。
4. **vtable 过滤**:图片/文件消息对象走同一 UP1,vtable 不匹配时不消费命令。
5. **接管点安全**:UP1 仅在发送时执行(空闲期零流量),补丁竞态窗口可忽略;
   实测微信 CRC 未检测(与 M2 结论一致:4.1.13 的 CRC 不覆盖 UP1 所在页)。

## 四、当前限制(→ M4 方向)

1. **搭车模式**:需要一条真实消息经过 UP1 才能改写(即"用户发一条,机器人才能发一条")。
   自主发送需 β 方案:调工厂 0x6EC830 构造消息对象 + 组 shared_ptr + 调 UP2 0x17A3620。
2. **长度受载体容量限制**:改写内容 ≤ 载体原字符串 cap。超长内容需扩展:
   载体选择(发长消息搭车)或实现 heap 重分配(需匹配微信的 operator new/delete)。
3. **wxid 长度**:群聊 id(如 `12345678@chatroom`,>15B)要求载体也是堆分配的
   wxid 字符串(cap>15)才能改写。
4. 未做多命令并发/优先级、未做发送结果回执(可 hook CORE 返回值或监听 DB)。

## 五、遗留风险

- 微信更新会改变所有 RVA(prologue 校验会拦截并拒绝,属安全失败)
- 长期驻留的注入模块可能被微信后续版本的行为检测(与外挂同理,自用风险自担)
