## 〇、终极结论(本项目最关键成果)

### 消息对象(0x798 字节)完整布局 — 静态构造器与运行时转储双重验证

```c
struct WeixinMessageObject {          // vtable → rva 0x8BDF0F8
    /* +0x000 */ void* vtable;
    /* +0x008 */ {self, ctrl} 引用对 (enable_shared_from_this);
    /* +0x018 */ std::string s1;      // (运行时空)
    /* +0x038 */ std::string s2;
    /* +0x058 */ std::string s3;
    /* +0x078 */ std::string s4;
    /* +0x094 */ int32 flag1;         // =1
    /* +0x09C */ int32 flag2;         // =7
    /* +0x0B0 */ std::string wxid;    // ★ 目标 "filehelper"
    /* +0x118 */ int32 flag3;
    /* +0x6F8 */ std::string token;   // 36字节 二进制 (msgId/凭据)
    /* +0x758 */ std::string content; // ★★ 消息正文 明文 ("M6688", size@+0x768, cap@+0x770)
    /* +0x778 */ std::string extra;   // (运行时空)
};
```

构造器链:`0x7589E0`(从源记录拷贝 +0x758/+0x778 两串)← 工厂 `0x6EC830`(27 调用者)。
运行时证据:UP1(0x1790970) 的 r8→shared_ptr.obj,+0x758 处 "M6688" **明文在列**。

### 发送实现蓝图(M3 直接可执行)

**方案 α(✅ 已实装验证,2026-09-13)**:Frida 原型 `m3_send_proto.py`:
- hook UP1(0x1790970) → onEnter 持有 r8→消息对象 → vtable 校验(0x8BDF0F8, BigInt 比较)
- `rewriteString(obj, 0x758, content)` / `rewriteString(obj, 0xB0, wxid)`:零分配原地改写
  (新内容 ≤ 原 cap;cap≤15 写 SSO 内联,>15 写既有 heap 缓冲;更新 +0x10 size;补 NUL)
- **实测**:载体 "M6688" 被改写为 "M3改写成功" 后放行,气泡回显即为改写内容 —
  序列化/网络/落库/UI 全管线采用改写后对象,发送原语成立
- 命令通道:`m3_cmd.json` 轮询 → RPC 入队;vtable 不匹配(图片等非文本对象)不消费命令
- 工程坑:`BigInt !== NativePointer` 恒真 → vtable 校验必须 BigInt vs BigInt(`base.add(rva).toString()`)

**方案 β(主动构造,风险更高)**:调工厂 0x6EC830 建空对象 → 填 +0xB0/+0x758 →
构造 shared_ptr → 调 `UP2 0x17A3620(mgr, out, vector{obj}, 0)`;mgr 实例运行时可由任意既有 hook 捕获。

### 原生 DLL 移植可行性(M3-β 已勘察)

UP1 前 17 字节 = `push rbp/r15/r14/rsi/rdi/rbx + sub rsp,0x78 + lea rbp,[rsp+0x70]`
——全部可搬移(无 rip 相对引用,push 顺序保证 rsp 语义一致),**17 字节 stolen-bytes 内联 hook 可行**。

## 一、最重要的结论(一句话版)

**微信 4.x 的"发送"不是单一函数,而是一条对象流水线**:
UI 构造"消息对象"(含 wxid+内容) → 发送家族函数将其组装成"发送任务" → 任务按 wxid 哈希入管理器队列 → CORE 按会话驱动 → CGI 组包(`/cgi-bin/micromsg-bin/newsendmsg`)→ mmtls → 网络。

**任务对象不含正文**(纯簿记:前缀/引用对/wxid 副本/回调),正文在消息对象里随对象全程流转。

## 四、工程教训(血泪换来的可复用规则)

### 1. Frida 侧两大崩溃源(已定位、已修复、勿再踩)

| 崩溃 | 根因 | 修复 |
|---|---|---|
| frida-agent 0xc0000005 @0x9cbb5(×3) | ① `readUtf8String` 直读会被并发释放的内存 ② `send()` 序列化含**未配对代理字符**(U+D800-DFFF)的 JS 串 | 全部改 `readByteArray` 单次拷贝+副本解码;输出串强制过滤代理区+截断 64 字符 |
| CGI 层 hook 必崩(0x3A25E80/0x3A2A770) | 函数头含 Frida 重定位器无法安全搬运的指令 | **放弃内联 hook 这两个函数**,改静态分析或下层锚点 |

### 2. 安全区/危险区

- ✅ hook 系统DLL(ws2_32)安全;✅ hook 0x17xxxx/0x39Bxxx/0x6Axxx 区多次实测安全
- ❌ hook 0x3A2xxxx CGI 层 = 100% 崩(3/3)
- 微信 CRC 并未检测到我们的 hook(三次死因全是 frida 自身)

### 3. 方法论

- DR 硬件断点有**线程池盲区**,"零命中"结论不可信(Frida 全线程覆盖推翻了 wx_bp4/5 的误判)
- .pdata 异常表(496,938 条)可离线反查任意 RVA 的函数边界——比 Ghidra 快几个数量级
- 拍脑袋算地址必错:0x92E103A8−0x89B60000 我算错过一次(0x925 vs 0x92B),**所有 RVA 必须用脚本算**
