# 二期工程计划策略书
## 从"只读监听"到"可发送消息"

> 项目:微信消息监控与自动化平台(基于 wechat-decrypt + 4.1.13.65)
> 前置:一期工程已交付只读消息监控器(V1 验收通过,3 秒级 → Web UI 已升级 30ms 级)
> 日期:2026-09-13 · 状态:**草案(待评审)**
>
> ⚠️ 合规声明:本项目仅供学习研究与个人账号自动化。发送能力一旦实现即具备"机器人"
> 特征,违反《微信软件许可及服务协议》,存在封号风险。**全程仅限测试小号。**

**一期遗留的关键教训**(直接约束二期设计):
1. 客户端侧的"伪装"骗不过服务端审批(四条技术路线全被拒)→ 二期**不再碰版本问题**,4.1.13 原生登录;

3. 服务端风控的真正触发点是**行为模式** → 发送功能的频率/节奏设计与技术同等重要。

## 二、目标定义

### 2.1 北极星目标
**在小号微信上,由外部程序触发,自动发送一条文本消息到指定联系人/群,全程无人工操作。**

### 2.2 分级目标

| 级别 | 能力 | 验收标准 |
|---|---|---|
| **S1** | 发送文本到"文件传输助手" | API 调用 → 消息出现在手机端,延迟 < 3s |
| **S2** | 按联系人/群定向发送 + @成员 | 连续 50 条无失败、无崩溃 |
| **S3** | 富媒体(图片/文件/引用回复) | 与手动发送效果一致 |
| **S4** | 无人值守稳定运行 | 7×24h 挂机,断线自动恢复,零封号警告 |
| **S5** | 收发闭环机器人 | 收到消息 → 规则/AI 处理 → 自动回复(一期的监听 + 二期的发送) |

### 2.3 非目标(明确不做)
- 群发/营销类批量行为(风控最高危 + 法律风险);
- 读取他人数据;
- 对主力账号的任何实验。

## 三、技术路线评估(含 2026-09-13 关键实测)

### 3.0 【实测】UI 自动化路线在 4.x 上已死

对 4.1.13.65 主窗口(Qt51514QWindowIcon,Qt 5.15.14)的 UIA 深度探测结果:
**整个窗口只暴露 1 个元素(窗口本身)** —— 无按钮、无输入框、无控件树。

结论:3.9 时代 wxauto 依赖的 UI Automation 通道,在 4.x 的 Qt 重写中被**主动关闭**。
这直接改写了路线优先级(社区普遍没意识到这点,因为多数人还停在 3.9)。

### 3.1 三条候选路线对比

| 路线 | 原理 | 可行性(实测) | 风险 | 能力上限 | 工期 |
|---|---|---|---|---|---|
| **A. 界面自动化(降级版:剪贴板+坐标)** | 激活微信窗口 → 固定坐标点搜索框 → 剪贴板粘贴联系人名 → 回车 → 粘贴内容 → 回车 | 🟡 **可行但脆弱**(UIA 死了,只能坐标点击;窗口必须前台、不可最小化、DPI/布局变化即失效) | 🟢 低(零注入) | 只能发文本/图片,S2 封顶 | 2-4 天 |
| **B. DLL 注入 + 调用内部发送函数**(wxhelper 4.x 版) | 注入 DLL → 定位 Weixin.dll 的发送函数偏移 → 构造参数直接调用 | 🟢 **可行**(社区已在 4.0.3 实现收发;4.1.13 无现成偏移,需自研发现管线) | 🔴 高(注入暴露 + 需对抗 CRC,但"只调用不改码"本身不触 CRC) | S5 全能力 | 4-10 周 |
| **C. 商业框架(千寻 Pro)** | 厂商维护的 4.x 适配 | 🟢 可用(支持 4.1.2.17,7 天试用) | 🟡 中(风控按厂商对抗水平) | S5 | 1 天 |

### 3.2 推荐策略:**双轨制**

```
短期(S1 立即要): 路线 A 剪贴板自动化 —— 2-4 天交付,零注入零封号风险
长期(S3-S5):     路线 B 注入 + 偏移发现管线 —— 主工程,分里程碑推进
保底:            路线 C 千寻 7 天试用 —— 与 B 并行评估,B 里程碑连续跳票时切换
```

理由:A 路线用最低风险验证"发送后的风控反应"(这本身是宝贵数据);
B 路线是能力正解但周期长;C 是止损阀。

## 四、路线 A 实施方案(短期:剪贴板自动化)

### 4.1 原理
微信窗口在前台时,聊天输入框是普通焦点控件。流程:
```
FindWindow(Qt51514QWindowIcon) → SetForegroundWindow
→ 模拟 Ctrl+F → 剪贴板写入联系人名 → Ctrl+V → Enter(搜索)
→ Enter(进入会话)→ 焦点落输入框
→ 剪贴板写入消息内容 → Ctrl+V → Enter(发送)
```
### 4.2 关键风险与对策
| 风险 | 对策 |
|---|---|
| 坐标漂移(DPI/分辨率/窗口尺寸) | 相对坐标定位(以窗口矩形为基准)+ 启动时强制窗口尺寸 |
| 中文输入法干扰 | 全程剪贴板粘贴,绝不 SendKeys 直敲中文 |
| 用户正在用电脑(焦点抢占) | 限定"空闲时段执行"或专用虚拟桌面;这是 A 路线天花板 |
| 误发(搜索命中错误联系人) | 发送前截图回读确认会话名(OCR/像素比对) |

### 4.3 交付物
`sender_a.py`(uiautomation 仅做窗口管理 + pyperclip + SendInput)≈ 200 行,
接现有 Web 前端:聊天输入框**从禁用变可用**(前端已有,只加 API 转发)。

## 五、路线 B 实施方案(主工程:注入 + 内部调用)

### 5.1 技术分解(五个子工程)

#### B-1 偏移发现管线(核心难点,4-6 周)
目标:在 Weixin.dll(4.1.13)中定位 `发送文本消息` 函数。
```
方法一(动态回溯,我们已有全部技能):
  小号手动发一条消息 → x64dbg/CE 对收发相关数据下断
  → 回溯调用链 → 定位最终 send Call → 记录偏移
  (一期的硬件断点/IOCTL 拦截脚本直接复用!)

方法二(符号恢复,站在 RevokeHook 肩膀上):
  RevokeHook 项目已解决 4.x 的"符号恢复+字符串解密+自动偏移搜索"
  (github.com/EEEEhex/RevokeHook,持续更新至 2026)→ 移植其搜索逻辑

方法三(社区情报):
  易语言论坛 vx_hook 4.0.3 偏移表(Weixin.dll+偏移的收消息点等)
  + DbkeyHook(4.0.3.39+)源码参考
```
**已知情报**:4.x 核心库 WeChatWin.dll → **Weixin.dll**;R3 层 CRC 检测存在;
4.0.3.39+ dbkey 用后即释放;消息底层仍是 mars/protobuf。

#### B-2 注入方式选型(对抗注入检测的关键)

| 方式 | 模块列表暴露 | 实现难度 | 评价 |
|---|---|---|---|
| 远程线程 LoadLibrary | 🔴 出现陌生 DLL 名 | 低 | 教学用,不采用 |
| **DLL 劫持(ilink2.dll 代理)** | 🟢 显示为"原生组件" | 中 | **推荐**(RevokeHook 同款;转发原 DLL 全部导出) |
| 手动映射(无模块) | 🟢 完全隐形 | 高 | 备选(需自实现重定位) |

ilink2.dll 代理原理:微信启动加载 `ilink2.dll` → 我们的假 DLL 转发全部调用到
真 DLL(`ilink2_real.dll`)→ DllMain 里启动线程做初始化。

#### B-3 发送 API 实现
```
DllMain → 等待微信初始化完成 → 按 B-1 偏移定位 SendTextMsg 函数
→ 起本地 socket(复用 wxhelper 架构:HTTP :19088 风格)
→ HTTP POST /sendtext {wxid, content}
   → 构造参数(注意 4.x 的 wxString 实现可能与 3.9 不同,需逆向确认)
   → 调用函数
   ⭐ 关键原则: 只调用,不修改任何字节 → 天然免疫 CRC!
```

#### B-4 检测对抗(按需启用,不过度设计)
| 检测 | 对策 | 优先级 |
|---|---|---|
| 注入的模块暴露 | DLL 劫持已解决 | P0(选型自带) |
| R3 CRC 代码校验 | **只调用不修改** → 无需对抗;若需 Hook 收消息回调则用 **VEH 无痕 Hook** | P1 |
| 调试器检测 | 二期不用调试器常驻(偏移发现期用完即撤) | P1 |
| 行为风控 | 频率限制(≥人工节奏)、随机延迟、夜间静默、多账号轮换 | P0(持续) |

#### B-5 工程化
- HTTP API 与一期 Web 前端打通(`/wx` 的输入框从禁用变可用);
- 发送队列 + 失败重试 + 速率限制器;
- 崩溃保护:DLL 内所有调用套 try/except,异常不拖垮微信。

### 5.2 里程碑

| 里程碑 | 内容 | 预估 | 止损条件 |
|---|---|---|---|
| **M1** | ilink2.dll 代理 DLL 注入成功且微信无异常 | 1 周 | 微信频繁崩溃/检测弹窗 → 转手动映射或路线 C |
| **M2** | 定位到发送函数(静态+动态双重确认) | 2-4 周 | 4 周无进展 → 路线 C |
| **M3** | S1 达成(发一条到文件传输助手) | M2+1 周 | — |
| **M4** | S2 达成 + 72h 稳定 | 2 周 | 封号 → 停止,复盘风控模型 |
| **M5** | S4/S5(无人值守 + 收发闭环) | 持续迭代 | — |

## 七、决策点与止损

```
开工前:   路线 A 先行(2-4天) → 用最低成本验证"发送行为的风控反应"

M2 失败:  4 周找不到发送函数 → 停止自研,千寻转正
M4 后:   稳定运行 2 周 → 评估是否值得把主力账号迁入(默认:否)
```
