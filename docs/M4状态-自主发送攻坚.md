| 尝试 | 执行线程 | 结果 |

### 崩溃根因(已精确定位)

崩溃函数 `0x462B70`(0xDE 字节)开头即读微信 TLS:

```asm
mov eax, [rip+0xB173EF4]      ; _tls_index @ Weixin+0xB5D6A70
mov rdx, gs:[0x58]            ; ThreadLocalStoragePointer
mov rax, [rdx+rax*8]          ; Weixin 每线程 TLS 块
mov rdx, [rax+0x1F0]          ; ★ 会话上下文 (惰性构建, 非空才继续)
cmp dword [rax_ctx+0x388], 3  ; ← 崩溃指令: 上下文链不完整时解引用非法
```

**结论**:发送管线的代码依赖**惰性构建的 TLS 会话上下文**。只有真正跑过发送管线的线程
(聊天窗口逻辑线程 0xA0BC)拥有完整上下文;但它是一个**不泵消息的工作线程**
(消息钩子永不触发、APC 永不回调)——天生无法从外部注入执行时机。

## 六、v7-v11 攻坚记录(2026-09-13 深夜续)

### 里程碑 1: TLS 整块移植 ✅ (根治了线程崩溃)

实测 v7/v11: **UP1 完整管线干净返回,err=0,微信稳定**——线程崩溃问题根治。

### 里程碑 2: clientMsgId 语义破译 ✅

消息对象 +0x6F8 的 36 字节 token = **标准 UUIDv4 字符串**(带连字符,小写),
每条消息随机生成(3 条真实消息 3 个不同 UUID)。v10 起自主发送时自动生成新 UUID。
(3 样本: 533dd774-fa34-417c-8895-0484f086c323 / 51a5ab7b-7f23-4eb0-a289-1a3bfa9b27e8 / 66cb2da4-...)

### 里程碑 3: 工厂初态画像 ✅ (DUMPNEW)

工厂对象出厂即有: 正确 vtable、flag94=0/flag9C=1(与真实一致)、预生成 UUID token、
空 wxid/content。**只需填 wxid + content 即与真实消息对象状态一致**。

### 未攻克: 消息被下游静默丢弃

v11 最终实验: AUTO 全链路干净执行(transplant→factory→fill→UP1→restore, err=0),
微信稳定不崩——但:
- 本地无气泡(UI 层未感知,符合预期)
- **手机端文件传输助手也无此消息** → 消息未到达服务器
- 下一条真实发送也没把它带出(任务已被管线内部丢弃, 非滞留)

### 丢弃点分析(下次继续的抓手)

UP1 只是**入队**(5ms 返回,网络发送是异步的),丢弃发生在 CORE→CGI 之间。
排查顺序:

2. 对比真实任务与自制任务在 CORE 处理时的字段差异(重点: 四个空字符串之外

3. 反编译 0x17F4FC0 (StartSendMessageSyncStage) 的完整流程,找 CGI 提交的
   前置条件枚举
4. 注意: DUMPNEW 在未移植线程上调用工厂会污染会话状态(v10 事故根因),
   一切工厂调用必须在移植状态下进行

### 已确证

1. **UP1 有异常处理**(unwind flags: UNW_FLAG_EHANDLER=1, handler@0x72DE01C)
   ——"主体跳过 ctor/register/CORE 但正常返回"在机制上可能
2. **主体内部探针方案验证成功**: 在 UP1 体内三个 call 指令地址

3. **真实发送全轨迹**(tid 恒定, 全在一条线程):
   `TASK_CTOR → QUEUE_REG → MID → CORE → MID×2 → SYNC_A → MID×4 → QUEUE_REG → MID×2 → CORE → SYNC_B → MID×5`
4. **clientMsgId = UUIDv4**(3 样本互异, 生成策略正确)

  出现一次不符 → **Frida 探针与 DLL 原生补丁在同一函数家族上互相干扰**

### v12 方案 (下次会话第一步)

## 八、四轮对照实验(2026-09-14 凌晨)— 因果关系判定

### 实验设计

同一 DLL 源码,用编译开关控制钩子组合,双盲对比(观察者只知道存活/崩溃):
- E1: 仅 UP1 钩子(基线) | E2: UP1+TASK_CTOR 计数 | E3: UP1+QUEUE_REG 计数 | E4: UP1+双计数

### 结果矩阵

| 配置 | 补丁数 | 试验 | 结果 |
|---|---|---|---|
| E1 基线 | 1 | 1 | ✅ 稳定,发送正常 |
| E2 +TASK_CTOR | 2 | 1 | ✅ 稳定 |
| E3 +QUEUE_REG | 2 | 1 | ✅ 稳定 |
| E4 +两者 | 3 | 1 | ❌ 发送后崩溃(整机卡顿→闪退) |
| E4 复现 | 3 | 2 | ✅ 稳定 |

### 结论(修正之前的错误归因)

1. **"钩子数量越多死得越快"是虚假相关** — v7 单钩子 63 秒崩过(缺 clientMsgId 的
   异步崩溃),v11 单钩子活了 32 分钟;E4 同配置 2 次试验 1 崩 1 存
2. **正确的结论:3+ 补丁状态下存在非确定性的崩溃风险**(约 50%/分钟,样本量小),
   机制推测为保护机制的完整性扫描与外来补丁的竞态(卡顿 = 扫描 188MB .text 的
   全量比对;StackHash = 执行被处置的 trampoline 页),确切机制未证明
3. **单/双补丁在小样本内未观察到崩溃,但长期风险未量化**

### 工程决策(基于以上)

- **M3 搭车发送的单钩子配置仍是最稳的交付形态**,但必须配 **崩溃恢复监督进程**
  (监控微信存活 → 崩溃即重启+重注入),把非确定性崩溃变成可管理的运维事件
  ——这也是现实中微信机器人框架的标准做法
- 丢弃点诊断改用 **DR 硬件断点计数器**(零字节修改,完整性扫描原理上不可见),
  内联钩子计数器方案废弃
- 之前"钩子数量"归因的错误教训:**每个崩溃样本必须单独取证近因,禁止把异质
  原因归并成单一变量** ——本次由用户质询发现,特此记录

## 九、M5 终章: DR 计数器实装 + 移植方案判死 (2026-09-14 凌晨)

### v14-v16 实验记录

| 版本 | 变更 | 结果 |
|---|---|---|
| v14 | DR 断点(管道线程) + VEH + C_helper 加 GetMyTlsCtx | ❌ 真实发送即崩 @Weixin+0x462C1E |
| v15 | VEH 加严格地址校验(触发地址+线程 DR 双匹配) | ❌ 33 秒后崩 @DLL+0x1E9B (GetMyTlsCtx 内) |
| v16 | 移除热路径 GetMyTlsCtx 调用 | ✅ 真实发送稳定 → AUTO 触发 @Weixin+0x462C1E |

### 关键勘误与真因

1. **v14/v15 的崩溃根因 = C_helper 热路径里新加的 GetMyTlsCtx()**:
   `mov 0x1f0(%rax),%rax` 读 tlsArray[12]+0x1F0 时踩进未映射内存
   (objdump 定位: 崩溃 IP = DLL+0x2E9B, 两个会话同偏移, 实锤)
2. **v16 的 AUTO 崩溃 @Weixin+0x462C1E = 与 v2 完全相同的 TLS 上下文链读取**
   ——尽管移植已经生效。结合 v7"返回后 10 秒崩"、v11"不崩但不送达":
   **管线在借用 TLS 上执行时会写入 per-thread 会话状态 → 污染被借用线程的
   上下文 → 延迟/立即崩溃, 且消息未真正送达服务器**
3. **移植方案判死: 读安全, 写致命。** 管线不是纯函数, 它更新线程绑定的
   会话状态机; 借用块执行 = 跨线程状态污染, 时序随机, 不可修复

### DR 计数器本身: ✅ 工作

- VEH + SetThreadContext 布防 + 严格地址校验(触发地址+线程 DR 双匹配,
  避免吞掉微信自身的 DR 异常) — 机制成立
- 但 AUTO 期间的管线执行本身不稳定, 计数器读数随崩溃丢失
- 保留在代码中 (v16), 后续若需要"读侧"追踪仍可用

### 自主发送的最终架构判定

管线必须在**拥有真实线程上下文的执行流**中运行。外来线程执行会污染状态。
可行路径只剩:
1. **搭车冲刷**(已可用): 正确线程上循环构造+调用, 一次载体 N 条消息
2. **寻找可借用线程的执行时机**: APC/消息钩子在发送线程上的触发条件
   (v5 实测发送线程不泵消息不警报 — 需要找聊天窗口线程并验证其 TLS)
3. **逆向线程上下文初始化**: 找到微信为新线程构建会话上下文的函数,
   在自家线程上合法构建 — 最彻底但工程量最大

## 十、裁决实验 (2026-09-14 01:38) — 移植路线正式判死

### 实验设计 (v17)

AUTO 前用 SuspendThread 冻结发送线程 (g_senderTid), 独占借用 TLS 块,
管线执行完毕后恢复。同时 DR7 改用全局启用位 (0xAA), 计数器暴露到 STATUS。

### 结果

```
[FREEZE] sender suspended (prevCount=0)   ← 发送线程已冻结, 独占借用块
[AUTO] factory + fills + clientMsgId ✓
崩溃 @Weixin.dll+0x462C1E                  ← 依然崩, 1 秒内
```

### 判决

**冻结发送线程 (完美互斥) 不能阻止崩溃 → 崩溃不是并发竞态, 是所有权语义问题。**

TLS 块 +0x1F0 的会话上下文链是**线程绑定的执行身份**:
- 链条深处对象引用发送线程自己的执行环境 (任务队列位置/调度标记)
- 换线程解引用 = 语义无效, 独占访问也无法挽救
- 比喻: 不是"两人同时改文档" (锁可解), 而是"别人的工牌刷不开你的门"

**因此**: TLS 移植 + 任何锁/同步手段 = 死路。管线必须运行在
**拥有真实线程上下文的执行流**中。

### 下一步方向 (更新)

真实发送的任务是被**派发**到工作线程执行的 (UP1 调用栈: 调度器 0x6EC950 →
处理器 0x19D14C0 → ...)。找到微信的**任务派发机制**, 把构造好的消息对象
通过同一派发通道投递 → 微信自己的线程池线程 (上下文合法) 执行完整管线。
即: 不再"借用线程", 而是"给微信的任务队列投递工作"。

## 十二、协程架构全解码 (M5 新方向第一夜成果)

### 核心发现: 微信 4.x worker 线程 = 协程调度器

真实发送的完整调用栈底部是 **coroutine.cc/co_core.cpp 的协程系统**:
- worker 线程由线程包装器 (0x72F241C) 启动: 绑定 runner 对象到 TLS+0x3C0
- 发送流程 = 一个协程 (co_main, 0x464950, 日志 tag "co_main"/"co_core.cpp")
- **TLS+0x1F0 = "当前运行中的协程" shared_ptr** (0x462B70 = GetCurrentCoroutine)
- 崩溃点 +0x388 = 协程对象的状态字段 (co_main 里写 3 = finished)
- **借用线程崩溃的真因**: 借用的"当前协程"指向发送线程已结束/挂起的协程
  → use-after-free → 一切移植崩溃的终极解释

### 协程对象布局 (0x510 字节, operator_new 分配)

```
outer:  +0x00 vtable (0x8B976D8)   +0x08 refs{1,1}   +0x10 inner...
inner (=outer+0x10):
  +0x350  body 描述符指针
  +0x358  完成回调函数
  +0x360  完成回调参数 (shared_ptr)
  +0x368/+0x370/+0x380  上下文对象三指针
  +0x388  状态 (co_main 结束时写 3)
  +0x4A0  id
  +0x4A8  name std::string ("coroutine_N" 默认名)
```

### 协程创建 API 链 (全解码)

```

```

### 真实用例 (发送管线自身的协程 spawn, @0xDB9150)

### 协程调度机制 (新发现)

1. **co_main 无直接调用者** — 协程通过**上下文切换**进入 (libco 风格:
   do_backup_stack_ 函数备份 sp..top 栈区间, 腾讯自研 libco 衍生)
2. **Sched_2 (0x462A80) = 调度器构造函数** — 初始化 DAT_18b5d8320/0x83a0

3. **创建器尾部的 FUN_180466360(&DAT_18b5d83a0, id, X, 0) = 按 id 注册协程**
4. **注册 ≠ 执行**: 协程注册后等待触发/唤醒; opts 三指针
   (+0x368/+0x370/+0x380) 极可能就是触发器/唤醒器 (真实 spawn 的
   opts = 发送流程控制器的 +0xF0 成员, 内含事件句柄)
5. **我们的协程没有挂接触发源 → 永远不被 resume**

1. **确定 opts 三指针语义**: 运行时 dump 真实 spawn 的 opts 结构

4. **方案 B**: 直接调用 resume 函数驱动我们的协程
5. **对照实验**: 运行时 hook CoCreate (0x45FCC0) dump 真实调用的

## 十三、M6 决定性突破: flag 参数 + 嵌套 UP1 端到端送达 (2026-09-14 下午)

### 突破结论(本轮最重要发现)

**UP1 的第 4 参 flag (r9) 是 CGI 网络提交的开关。** 历史上所有"任务被静默丢弃"的实验
(v7-v11 AUTO、嵌套发送) 全部硬编码 flag=0 → 本地消息创建+状态机闭合("已发送")但
网络提交从不发生。flag=1 时完整管线端到端走通: 本地→CGI→服务器→移动端。

### 判定性实验链 (v26-v29)

| 版本 | 变量 | 结果 |
|---|---|---|
| v26 双补丁(UP1+SyncStage) | 嵌套A(PC有/移动端无) + B发送中崩 | 崩疑云#1 |
| v27 单补丁+WrFresh无恢复 | 同样行为, 延时崩 | 排除UAF恢复写; 排除双补丁 |
| v28 嵌套+全新UUID | C"已发送"但移动端无, 延时崩 | 排除 clientMsgId 去重假说 |
| **v29 嵌套+继承外层flag(=1)** | **E 端到端送达移动端** | **flag=门控实锤** |

### 静态定位(事后归因)

- UP1 主体结构(0x1790970, 0x204 字节): new 0x100 task → TaskCtor(0x39B94B0)
  [flag 存至 task+0xB8] → QUEUE_REG(0x17948C0, mgr+0xBF8→+0x90 队列)
  → CORE(0x1795500 同步) → 结果提取
- TaskCtor 内 flag 字节随任务走全程; CORE 内两处队列入队(+0x90 / +0xD0 网络队列)
- SyncStage(0x17F4FC0) 门控谓词: `FUN_181E2F4A0(obj)` = 读 obj+0xB8 字节, 0→短路
  (注意: +0xB8 落在 wxid std::string SSO 缓冲内, 语义待深究)
- obj+0x388 state=0(发送前), obj+0xB8=0x65('e', "filehelper" SSO 第8字节) — 实测快照

### 崩溃序列的完整归因(全部实测)

1. **v26/v27/v28 的"延时崩"**: 嵌套调用后异步网络阶段的对象别名/状态污染
   (flag=0 的任务卡死在网络队列, 之后触碰已被外层消息生命周期改写的 obj)
2. **v32"点击发送瞬间崩"**: 等待钩子(0x7329A7C)在 UP1 body 执行中途触发冲刷
   → body 中途嵌套第二个 UP1 = 深层重入(v29 验证的安全时机是 body 开始前)
3. **wait_stub 栈对齐 bug**: 5 push + sub 0x28 → C_auto 入口 rsp%16=0(应 8)
   → 修复: sub 0x30。注入后秒崩的近因(或与 3 补丁保护器叠加)
4. **3 补丁(UP1+PROC+WAIT)高危**: 与第十二节 E4 实验一致, 最多 2 补丁

### v33 工程形态(当前)

- 双补丁: UP1(入口) + WAIT(线程池等待函数 0x7329A7C, 栈采样定位, 暂不冲刷)
- C_helper(UP1 入口安全窗口):
  1. SEND 队列: 嵌套模式(对象复用+WrFresh, 前 N-1 条) + 最后一条改写
  2. AUTO 队列: 工厂(0x6EC830)造独立对象 + 填 wxid/content/新UUID + UP1(flag=1)
  3. flag 策略: 继承外层真实调用 (g_flagLast, asm 桩捕获 r9)

- WrFresh: 永远新堆缓冲(HeapAlloc), 不读不写旧缓冲, 旧缓冲遗弃(泄漏无害)

### 完全无触发发送的剩余路线(下次继续)

3. **mgr 静态发现**: 摆脱"首次发送武装 mgr"依赖 (找 mgr 单例的全局存储)

## 二十一、0xFEA90 陷阱真身 + fd/锁 22 无效 (2026-09-15 凌晨)

### 陷阱真身 (精确反汇编)

0xFEA90 的指令 = `C7 04 25 00 00 00 00 37 13 00 00 C3`
= `mov dword ptr ds:[0], 0x1337 ; ret`
= **CRT invalid-parameter 的故意崩溃陷阱** (0x1337 = 标记魔数, 写 NULL 强制 AV 生成 dump)

```
→ 22 无效 (fd 表项=0 / 状态槽=0) → _invalid_parameter → 0xFEA90 陷阱 → 闪退
```

1. 日志静默标志 (TLS+0x360 bit0) **没有拦截这条日志** — 连续静默 (0.4s 间隔,
   129+ 线程) 下崩溃依旧 → 该日志路径不经过 FUN_180d9e810 检查, 或标志语义不同
2. 崩溃线程 = 执行器线程 (每次会话不同 tid: 46488/39852/16340/15572)
3. fd/锁 22 无效的原因待查: xlog 文件 fd 生命周期 / CRT per-thread 状态

### v68 三件套实现要点
1. **mgr 构造钩子 ×2** (0x1788920 / 0x178B5B0, 各偷 17 字节): 靠"扫 .text 中
   写 vtable 0x8E66148 的 lea 指令"定位。登录时触发, rcx=this=mgr。

2. **CoCreate P5 验证捕获**: 原 stub 直接存 P5 会被尾调用污染 (抓到过 URL 串)。
   改为 C_cocap 验证: P5+0x20 处的 exec 候选, 其 vtable 必须等于 0x8D4CDE8
   (exec 类, 与 coro+0x368 实测一致) 才接受。
3. **模板磁盘缓存**: C_helper 捕获模板时自动 WriteFile 存盘 (0x798);
   INIT 时若文件存在则加载。跨会话复用实测可行: 旧会话模板在本会话
   UP1(flag=1) 正常入网, 未崩溃, 移动端收达 —— 说明 UP1 只读模板中
   少数字段 (内容/目标/UUID 等已被 WrFresh 刷新), 陈旧指针未被解引用。

### 注入时序竞速
mgr 构造发生在登录完成时刻 (实测启动后 ~8s)。必须抢在它之前装好钩子:
taskkill 后确认进程数归零 → 启动 → 0.3s 内找到带 Weixin.dll 的主进程 → 注入。
上一轮 0.6s 时抓到退出中的旧进程 (注入被拒 failed:5) —— 排除旧 PID 是必须的。

- template.bin 若因微信版本升级/会话密钥轮换失效 (表现为发送无达或崩溃):
  重新发一条消息即自动刷新存盘 (C_helper 每次捕获都会覆盖写)。
- Weixin.dll 更新后所有 RVA 失效, 需重新定位 (vtable 扫描法可自动化)。

## 三十六、图片: 组装器结构捕获 + 保护者边界确认 (2026-09-15 晚)

### 组装器 (0x19D14C0) arg1 结构 (钩子捕获成功)
