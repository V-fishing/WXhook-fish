## 一、核心命题与设计哲学

### 1.1 命题

> 在微信 4.1.13.65 进程内部,获得"以微信自己的身份发送消息"的能力,
> 并以 HTTP API 形式暴露给外部(一期 Web 前端 / Python / AI)。

### 1.2 三条设计哲学(一期实战换来的)

| 哲学 | 来源教训 | 工程落点 |
|---|---|---|
| **① 只调用,不修改** | 一期破过两层自检,深知微信对"被改"极度敏感 | 发送 = 调用微信**自己的函数**,内存零修改 → R3 CRC 天然查不到 |
| **② 借位不造位** | 4.x 逆向是"换地图"不是"新大陆":3.9 架构原样适用 | 复刻 wxhelper 三段式,只重做"偏移"这一层 |
| **③ 隐身于正常** | 一期实测:纯读内存微信无感知;写内存/改文件立即触发 | 注入用 DLL 劫持(模块列表显示为原生组件) |

### 1.3 成功的唯一定义

小号微信登录状态下,`curl http://127.0.0.1:19088/sendtext -d '{"wxid":"filehelper","content":"hi"}'`
→ 手机文件传输助手出现 "hi" → **全程微信无任何异常表现**。

## 四、目标架构设计

```
┌──────────────────────── 微信进程 (Weixin.exe 主进程) ────────────────────────┐
│                                                                              │
│   Weixin.dll (微信本体, 198MB)                                                │
│     ├── GetSendMessageMgr ──┐                                                │
│     ├── SendTextMsg         │ ← 一期偏移发现管线定位(§6)                       │
│     ├── FreeChatMsg ────────┘                                                │
│     └── (收消息路径/DoAddMsg…后续扩展)                                         │
│                                                                              │
│   ilink2.dll ← 被微信正常加载(伪装位)                                          │
│     └── 我们的代理 DLL:                                                        │
│          DllMain → CreateThread(初始化等待) → 微信启动完成                      │
│                  → 按 §6 偏移表装配函数指针 → 启动 HTTP 服务 (:19088)           │
│                  → Manager::SendText/SendImage/... (复刻 wxhelper)            │
└──────────────────────────────┬───────────────────────────────────────────────┘
                               │ HTTP API(wxhelper 兼容格式)
┌──────────────────────────────▼───────────────────────────────────────────────┐
│  外部世界:  一期 /wx 前端(发送框激活) · Python Bot · curl · AI(MCP)              │
└───────────────────────────────────────────────────────────────────────────────┘
```

**设计原则**:DLL 内**只做两件事**——偏移装配 + API 暴露;所有业务逻辑(队列/风控/日志)在进程外的 Python 层(一期框架),DLL 保持最小暴露面。

## 五、关键技术一:三段式发送调用

### 5.1 wxhelper 3.9.5.81 的发送实现(黄金蓝图,逐行解读)

```cpp
INT64 Manager::SendTextMsg(const std::wstring& wxid, const std::wstring& msg){
  prototype::WeChatString to_user(wxid);   // ① 微信自己的字符串结构(见 5.2)
  prototype::WeChatString text_msg(msg);

  // ② 三个函数:基址 + 偏移(3.9.5.81 的值,4.x 全部要重找)
  UINT64 mgr_addr  = base_addr_ + 0x8c00e0;   // kGetSendMessageMgr
  UINT64 send_addr = base_addr_ + 0xfcd8d0;   // kSendTextMsg
  UINT64 free_addr = base_addr_ + 0x8aaa00;   // kFreeChatMsg

  char chat_msg[0x460] = {0};              // ③ 消息对象:0x460 字节定长栈结构,必须清零
  UINT64 temp[3] = {0};

  // ④ 三段式:拿管理器 → 填充并发送 → 释放
  mgr();                                                    // 返回 mgr 实例(RCX 传递)
  send(&chat_msg,              // ChatMsg*      (0x460 定长,栈上)
       &to_user,               // WeChatString* 接收者
       &text_msg,              // WeChatString* 内容
       &temp,                  // 辅助指针(3.9 传 3 元数组)
       1, 1, 0, 0);            // 4 个标志位(含义待 4.x 逆向确认)
  free(&chat_msg);             // ⑤ 不 free 会内存泄漏,长期挂机必须调
}
```

### 5.2 WeChatString 结构(3.9 实测布局)

```cpp
struct WeChatString {
    const wchar_t* buffer;    // UTF-16 内容指针
    UINT32 length;            // 字符数(不含 \0)
    UINT32 max_length;        // 容量(微信按 (len|0xF)+1 分配)
    // 3.9 还有占位字段…
};
```
**4.x 适配点**:① 该结构可能整体变(4.x 换了字符串实现?待逆向确认);② 若变为
C++ std::wstring 直接传,反而更简单。**这是 M2 的第一个验证点**。

### 5.3 4.x 未知量清单(M2 要逐个测定)

| 未知量 | 测定方法(§6 管线) |
|---|---|
| GetSendMessageMgr / SendText / FreeChatMsg 偏移 | 动态回溯 + 特征码(主攻) |
| ChatMsg 结构大小(0x460 → ?) | 断点命中时观察栈帧分配大小(`sub rsp, 0xN`) |
| WeChatString 布局是否变化 | 断点处读寄存器指向的实参内存 |
| send 第 4-8 参数含义 | 对照手动发送时寄存器/栈快照 |
| 管理器是否需要"账号就绪"前置状态 | 登录前后分别调用对比 |

## 六、关键技术二:偏移发现管线

> **这是全项目唯一的真攻坚点。** 三法并用,互为验证。

### 6.1 方法一:动态回溯(首选,一期技能直接复用)

**核心思路:微信发消息必经某函数 → 在"消息内容"被引用的时刻停下 → 回溯调用链。**

```
准备: x64dbg 附加微信(或用我们一期的调试器脚本) + 小号准备发一条独特文本

步骤:
1. 小号发出独特文本 "ZXBENCHMARK2026"(此前全网无此串)
2. 微信进程内存搜索该 UTF-16 串 → 得到地址 A(消息内容缓冲区)
3. 对 A 下硬件读取断点(DR0,一期 hw_watch.ps1 直接复用!)
4. 自己再发一条消息(或手机上操作触发重发场景)
5. 断点命中 → 读 RIP → 这是"读取消息内容"的代码
6. 沿调用栈向上回溯(rsp 链解栈回溯),过滤 Weixin.dll 内的返回地址
7. 找到"参数里带内容+接收者"的层级 → 即发送函数候选
8. 验证:该函数偏移 + 调用参数模式与 3.9 三段式同构(三函数相邻、ChatMsg 定长栈对象)
```

**为什么先找"接收路径"更稳**:论坛 vx_hook 已给出 4.0.3 的**收消息点**
(`recv` 特征)与 10 条调用关系——收发在微信内部共享底层(mars/protobuf),
从收路径的相邻函数往往能枚举到发路径。**先收后发,降低盲找成本。**

### 6.2 方法二:静态特征码(版本迁移的长期方案)

```python
# 已知 4.0.3 社区特征码(起点样本):
b"49 8B 5D 00"
b"66 0F 1F 44 00 00 48 8B 3B 48 85 ??"
# 方法: 在 4.1.13 的 Weixin.dll 上跑这些特征 → 命中点周边做调用图分析
# → 与 4.0.3 的 10 条调用关系模式匹配 → 推断 4.1.13 对应函数
```
配套自研工具:`sig_scan.py`(一期 scan_pattern 的离线文件版,半天工作量)。
**长期价值**:特征码方案让"微信更新→重新适配"从周级降到小时级。

### 6.3 方法三:符号恢复(RevokeHook 路线,最系统)

RevokeHook 已实现:4.x 字符串解密(微信 4.x 把关键字符串加密存储,运行时解密)
→ 解密后即可按字符串引用定位关键结构 → 自动搜索函数偏移。
**行动计划**:环境恢复后 clone 源码,提取其:解密算法、偏移搜索引擎、ilink2 代理模板。

### 6.4 验证方法论(每一步都要交叉确认,一期的教训)

| 验证对象 | 验证手段 |
|---|---|
| 找到的函数是"发送文本" | 断点处改参数内容(临时)→ 手动发送 → 消息内容被改 = 实锤 |
| ChatMsg 大小 | 断点命中时看 `sub rsp, 0xN` 分配值 / 结构体成员访问越界点 |
| WeChatString 布局 | 发送"ABCD" 断点处看参数指向内存的 `04 00 00 00, 08 00...` 头部 |
| 偏移在重启后稳定 | 重启微信 3 次,每次基址+偏移命中同一函数序言 |

## 七、关键技术三:ilink2.dll 代理注入

### 7.1 为什么选 DLL 劫持

- 微信 4.x **正常启动就会加载** `ilink2.dll`(实测模块列表在案)→ 我们的同名 DLL 会被**正常加载**;
- 模块列表里它就是"微信自己的组件"→ 模块扫描检测无效;
- 相比远程线程注入:无 `CreateRemoteThread` 调用痕迹、无跨进程写入。

### 7.2 实现要点

```
1. 把原版 ilink2.dll 改名 ilink2_real.dll(随微信目录分发脚本处理)
2. 生成代理 DLL:枚举原 DLL 全部导出 → 逐个生成转发代码
   (工具: RevokeHook 有现成模板; 或用导出表解析自动生成 .def + 转发实现)
3. 我们的 DllMain(DLL_PROCESS_ATTACH):
   ⚠️ 铁律: DllMain 内不做任何重活(加载器锁!)
   → 只 CreateThread(后台线程)
   → 线程内: 等待微信初始化(轮询 Weixin.dll 模块就绪+登录态)
   → 装配 §5 函数指针 → 启动 HTTP :19088
4. 兼容性: 转发必须覆盖原 DLL 100% 导出(序号导出也要),否则微信功能损坏
```

### 7.3 分发与加载

不修改微信任何文件(一期教训:改文件触发自检!)——
**只在我们自己的微信副本目录放置代理 DLL**(用户目录 `E:\weixin-hook-4.1.8\WeChat\` 是自解压副本,天然隔离),官方安装目录永不触碰。

## 八、关键技术四:检测对抗

### 8.1 分层对抗表

| 检测层 | 微信手段 | 我们的对策 | 状态 |
|---|---|---|---|
| 文件自检 | 一期实测两层校验 | **不碰任何微信文件**(代理 DLL 是"新增",且放在副本目录) | ✅ 已解 |
| R3 内存 CRC | 4.x 实测存在(社区确认) | **只调用不改码**(§5)→ 无需对抗;若将来 Hook 收消息回调,用 **VEH 无痕 Hook**(论坛 4.0.3 实战方案,绕过 inline patch) | 设计就绪 |
| 模块扫描 | 扫陌生 DLL | ilink2 伪装(§7) | ✅ 设计就绪 |
| 反调试 | 低版本实测会自杀 | 二期偏移发现期用完调试器即撤;DLL 运行态无调试需求 | ✅ 流程解决 |
| **行为风控(服务端)** | 收发模式/频率/时段分析 | **速率限制器**(≥人工节奏、随机抖动、夜间静默、日上限);**这是无法用技术"绕"的,只能"配 合"** | ⚠️ 长期对抗 |

### 8.2 VEH 无痕 Hook 原理(预留技术,收消息毫秒级化时启用)

```
传统 inline hook: 改函数头 5 字节 → CRC 校验和变了 → 被抓
VEH hook:        注册 Vectored Exception Handler
                 → 把目标页改为 PAGE_NOACCESS(页保护,非字节修改)
                 → CPU 执行到该页触发 EXCEPTION_ACCESS_VIOLATION
                 → VEH 拦截异常: 单步执行原指令(临时恢复保护)+ 收集数据
                 → 恢复 NOACCESS
                 → 代码字节从头到尾没变过,CRC 读到的还是原文!
```
